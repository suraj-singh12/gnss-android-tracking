# Repository agent instructions

Applies to the entire `gnss-android-tracking` repository. These are stable **working rules**, not a substitute for the checked-out source, current GitHub Issues or canonical documentation. If reality differs from an older note, verify the implementation and update the owning documentation; do not silently assume either is correct.

## 1. Current state and safe Git workflow

- Before edits, check `git status --short`, active branch, `git rev-parse HEAD`, upstream ancestry and a small relevant `git log`. Inspect the **current issue and PR state** using GitHub when available. Do not rely on SHA values, issue status or architecture summaries copied into old prompts.
- **Issue first, branch second.** Every finalized feature/fix must have one appropriately scoped GitHub Issue (or a deliberate set of linked, independently deliverable issues). Inspect existing issues for overlap and acceptance completeness before creating another. Do not create speculative feature branches or duplicate issues. Create exactly one independent working branch for each approved implementation issue, containing `devX` in its name (for example `feature/issue-22-devX-sync`). Branch naming is a convention, not permission to start implementation.
- **Historical field-tested stable reference (not a new-branch parent):** `d78ef85e689ca43281127599e814b04cb99aefc8` remains the operator-accepted field-tested application baseline as of 2026-10-15. Preserve this reference for provenance/comparison; it is **not** the default starting point for new work, and integration CI passing does not make an integration revision field-tested stable.
- **Mandatory latest-integration starting point (operator authorization 2026-10-19):** For every subsequently approved implementation issue, fetch the **latest remote HEAD of `integration/combined-upgrades` when the issue's `devX` branch is created**, check clean working state, history, ancestry and approved merged dependencies, and branch from that exact verified SHA. Record that SHA as the issue's reproducible parent. Do **not** start from `main`, the historical `d78ef85e` reference, a stale saved integration SHA or a different feature branch. This starting-parent authorization applies to current and deferred issues; it does **not** authorize implementation, PR merges, issue closure or releases.
- The combined testing/integration destination is **`integration/combined-upgrades`**. Feature PRs normally target that branch, **not `main`**. If integration advances after the issue branch is created, compare against its **latest accepted HEAD** and safely reconcile its integrated code, migrations and tests before proposing integration, with targeted regression coverage; avoid force pushes, silent code loss and unreviewed dependencies. Confirm the exact PR base/head and obtain operator approval before merging.
- **Never mutate `main` in any way without the operator's explicit, specific permission for that action.** This includes direct commits, workflow/configuration edits, PR merges, branch/ref updates, resets or other writes. “Proceed”, green CI, a feature request, issue completion, or permission to change another branch is not permission to touch `main`. Do not automatically merge into integration either; operator approval is required.
- **Stable is an operator acceptance decision, not a CI label.** Green checks and matched assets are evidence, not proof of field stability. Preserve the approved `d78ef85e` reference and do not call a new commit stable until the operator accepts it.
- Do not close issues, create releases, delete branches, reset shared state, force-push or rewrite unrelated commits without explicit approval. Leave unrelated working-tree changes untouched.
- Existing stacked feature/terrain PRs and other in-progress branches must not be merged, retargeted or overwritten incidentally. Check for overlaps before changing shared code.
- Implement one coherent approved issue per branch. If a feature is too broad, define independently testable linked issues before branching; if several changes form one inseparable acceptance outcome, keep them in one issue and execution. Open a reviewable PR with linked issue, exact head SHA, tests and limitations. Wait for operator approval before integration.
- **Canonical agent-guidance source:** `chore/codex-repo-instructions` is a special documentation-only branch whose entire tree contains `AGENTS.md`. Maintain the universal instructions there. Never merge or checkout that single-file tree over an application branch. Before issue work, compare the working branch's `AGENTS.md` to the approved canonical version and intentionally synchronize only the file if needed, in the issue branch; record its guidance commit SHA. An update to the canonical file is not automatic approval to modify feature branches or `main`. Feature specifications belong in GitHub Issues, not in this universal policy.

## 2. Canonical reading order (read only what the task needs)

1. **Read `AGENTS.md` at the start of every Codex task**, compare it with the approved guidance branch and current operator instructions. Report any contradictions or outdated rules to the operator before implementation. Do not silently assume the file remains aligned.
2. **The current GitHub Issue/PR** for feature requirements, acceptance conditions and dependencies; inspect its latest comments and relevant recent code changes.
3. **`README.md`** for the product map, only when orientation is needed.
4. **`docs/architecture.md`** for cross-component authority, recording, data flow and persistence; consult affected sections, not necessarily the entire file.
5. **`protocol/protocol-v1.md`** and `protocol/fixtures/` for wire contracts or compatibility work. This is the normative cross-app contract.
6. Component guidance **only for components touched**: `android/README.md`, `command/README.md`, `test-tools/README.md`, `test-tools/integration/README.md`, `android/DEVICE-ACCEPTANCE.md`. For UI changes also consult `docs/design-system.md`, `docs/ui-acceptance.md` and `docs/ui-preservation-matrix.md`.
7. Read the **actual relevant source, callers/callees, tests, configuration and recent diffs**. Broaden inspection only when dependency edges or a failing test justify it.

No generated “current architecture” snapshot or previous agent summary is authoritative. Source + present Git state + current issue + canonical contract establish the truth. Avoid repeatedly dumping/reading the whole repository, unrelated issues or all documents on every task. If using a retained understanding from earlier work, quickly verify the specific changed interfaces and upstream diffs before relying on it.

## 3. Preserve the system's authorities

- **Android** owns actual GNSS measurements, local Room durability, tracking sessions and outbound transmission. **Command** owns durable receipt/ACK, raw SQLite history, quality policy, recording windows, chronological projection, distance and display. `protocol-v1.md` owns interchange.
- Reuse and extend the existing architecture, canonical IDs, persistence, sender, transaction boundaries, evidence, correction/projection/checkpoint machinery and tests. Do not add competing databases, parallel tracking/recording authorities, duplicate queue engines or architecture rewrites without evidence that existing mechanisms cannot safely satisfy requirements.
- Preserve immutable original message/observation identities, session sequences, measurement timestamps, accepted/rejected reasoning, transactional **durable storage before ACK**, idempotent retries, retained raw data, SOS and its separate operator acknowledgement.
- Never invent GNSS fixes, connect recording/session/unknown gaps as real traveled distance, convert old history into fresh live position or claim synchronization solely because a request returned 200. Quality and operator recording controls remain authoritative.
- Field operation is **offline-first**: local Wi-Fi, no SIM/internet/cloud dependency, offline assets; Android and portable Command must work independently. Command source development must remain practical on macOS and Windows, separately from packaged/release binaries.
- The number of phones is **variable**. Use **20 simultaneous phones as the ordinary capacity/performance benchmark**, including a 21st joining later where relevant, but never hard-code a 20-device maximum.
- Android OS restrictions, background-service behavior, timing and battery limits must be represented accurately. A successful Linux CI cross-build is not proof of actual Android, macOS or Windows runtime behavior.

## 4. Efficient implementation and verification

- Inspect first, identify/reproduce a failure or measurable bottleneck, then implement the smallest coherent safe change. Prefer **one complete execution** covering targeted implementation, regression tests, self-review, documentation, commits and a review PR, rather than unnecessary staged re-prompts.
- Start with fast, relevant tests; use existing build/test caches when safe. Do not rerun expensive full suites after every small edit. **Before marking a PR ready**, run required complete regressions, end-to-end real Room/Sender → Command checks for cross-app changes, browser/UI tests for UI changes, and measured stress/race tests for concurrency/performance changes.
- Existing verification entry points: `cd android && ./gradlew testDebugUnitTest lintDebug assembleDebug --console=plain`; `cd command && go test -race ./... && go vet ./...`; `cd test-tools && go test -race ./... && go vet ./...`; `test-tools/integration/run.sh --console=plain`. Follow the component guides for setup, execution and any additional checks.
- For real cross-app integration, a skipped bridge test is **not** a pass. Keep unit tests, race checks, native-runtime acceptance, network fault injection and actual field validation distinct. Never fabricate counts, performance, timings, device reachability or verified artifacts.
- Maintain compatibility for old stored data and negotiated older protocol peers. Add tests for restart, error/ACK loss, duplicates, malformed input, partial synchronization, device churn, SOS/live priority and policy/recording boundaries as appropriate.
- Prefer profiling to speculative performance rewrites. Record comparable baseline/after metrics, exact workload and environment, including bytes, observation counts and stage timings when throughput is involved.
- Update the **existing owning documentation** for any changed behavior; avoid parallel documents or duplicated instructions. Preserve the established design/UI vocabulary and existing interfaces unless the issue explicitly authorizes a change.

## 5. Pull request and reporting contract

- Use a focused issue-linked PR normally **to `integration/combined-upgrades`**, unless the operator explicitly approves another destination. Re-fetch the integration target before PR review, reconcile approved upstream updates safely (without rewriting unrelated/shared branch history), then verify the exact parent/source/test and current target SHAs. Review the actual diff for scope, data loss, security, compatibility and unintended rewrites.
- Use the existing integrated validation workflow, adjusted for integration-targeted PRs as needed. Produce Android APK, macOS ARM64 and Windows AMD64 Command acceptance assets from the **same exact tested source SHA**, with manifest/checksums and honest build/signature evidence where relevant. Prefer reusing existing workflows instead of duplicating them.
- Release/acceptance gates must distinguish Android real-device behavior, macOS native Command, Windows native Command, browser UI and offline/LAN operation from cross-compiled CI artifacts. Explicitly list platforms not actually tested. Final report: root cause/requirements, concrete modifications, tests with pass/fail/skip, performance numbers where applicable, exact branch and commit, PR + CI/artifact links, unsolved issues, and field/native limitations. Never claim a future test, upload, merge or release has happened unless confirmed.
- Do **not** merge the PR or close its issue. Operator decides integration and ultimate release.

## 6. Mandatory UI/UX design intelligence and operator design gate (Issue #62)

**No application UI implementation before explicit design approval.** For any new or modified user-facing screen, control, workflow, interaction, layout or visual behavior, first prepare a design proposal, show it to the operator and stop. A request to implement a feature, previously approved unrelated design, or existing component convention does **not** constitute acceptance of a new visual design. After explicit approval of the specific proposal and scope, implement it in the linked issue; do not use approval as permission to merge. Pure documentation/prototyping and non-visual code work can continue without changing the app UI.

**Persistent repository intelligence, not repeated screenshot loops.** Read and maintain the existing `docs/design-system.md` (design language, screen ownership, component and navigation inventory, prior decisions and reference patterns), `docs/ui-preservation-matrix.md` (authoritative functionality/placement to preserve), and `docs/ui-acceptance.md` (evidence and quality gates). Prefer updating these documents and existing components over spawning parallel design documents, new controls, or a replacement architecture. Read only the affected portions and verify against current relevant source/PR changes before relying on them.

For each UI-impacting issue:
1. **Understand and scope:** locate the user goal, screen, ownership, existing component(s), navigation paths, adjacent experiences and backend safety/authority constraints. Record `keep / affected / proposed`. Check desktop/narrow/native layouts, empty/populated/loading/error states, disclosures, long text, keyboard/accessibility, SOS visibility and overlap.
2. **Research selectively:** consult authoritative Apple Human Interface Guidelines for clarity, hierarchy, progressive disclosure, layout and interaction quality, *adapted* to Android native conventions and Command's offline browser platform. Study proven, relevant map/time/operational applications when a problem is new; cite what pattern is applicable and why. Do not repeat research for already-settled patterns or imitate visual styling blindly.
3. **Design intentionally:** choose placement based on task frequency and importance. Preserve map-first work, status truth, safety access, no overwhelming permanent diagnostics, one consistent design language, reusable components, quiet surfaces and accessible controls. Use progressive disclosure for secondary/technical detail; ensure responsive behavior.
4. **Present exact, app-specific proposed UI:** show actual proposed GNSS layout and content—not generic reference images—with realistic controls, interactions, appropriate states, desktop/mobile as relevant and a clickable prototype where interactions materially affect the result. Label simulations and source revision; distinguish current captured evidence from proposed rendering. Explain what remains unchanged and what changes. **STOP for explicit operator selection/approval.**
5. **Only after approval:** implement against the frozen approved proposal, update the relevant existing design inventory and decisions, run targeted functional/accessibility/interaction checks plus proportionate rendered verification for substantial UI changes. Do not repeatedly screenshot-review already-settled unchanged components. Report any material visual divergence for a new operator decision instead of improvising.
6. **PR gate:** include issue link, approved design reference and decision, component reuse, affected states and verification evidence; do not claim screenshot fidelity, real-device behavior or design approval that was not actually obtained.

Operator intent: consistent and attractive professional UI, easy comprehension, high-value information in focus, little visual noise, discoverable secondary tools, and deliberate rather than merely functional interactions. Prefer Apple-style *principles* over copying an Apple appearance into GNSS.

## 7. UI proposal quality: reject before operator review (Issue #62, second pass 2026-11-01)

The operator rejected first-pass interactive proposals for duplicated facts, inconsistent components, overflowing labels, and uneven hierarchy. **The first-pass proposals are superseded, not approved implementation targets.** Never reuse their screenshots as proof of the present application. Use the exact latest relevant application branch/commit and inspect **current source and newly rendered live captures where possible**, explicitly distinguishing source inspection, old evidence, and newly captured evidence. A screenshot from an old/closed issue is not evidence of the current screen.

**Design acceptance is a hard gate before presenting even a proposal:**
- **Information economy:** one authoritative home for each fact and action within a workflow. Duplicating vital SOS status in an independent safety dock and its diagnostic record may be justified; redundant headings, modes, breadcrumbs, dates and generic help text may not. Give a concrete purpose to each repeated value.
- **Hierarchy:** protect primary task/canvas; show immediate actionable state first, context second and raw diagnostics only by an intentional disclosure. No raw JSON, large accordion, or permanently expanded technical block on the map.
- **Visual grammar:** use shared components/tokens and common labels, radii, spacing and interaction semantics; do not invent a new miniature UI language in each feature. Do not trade visibility or accessibility for ornamental minimalism.
- **Bounded rendering:** test realistic longest names, dates, translated/large text, errors, empty/loading/overflow, touch and keyboard, all relevant panel states. No unintentional clipping, horizontal page overflow, off-screen actions, obscured SOS, multi-line controls that collide, or content hidden below sticky rails. A deliberately scrollable content area must be visibly bounded, keyboard-reachable and retain important actions.
- **Responsive architecture:** choose different arrangements for compact/wide layouts where needed; never merely compress desktop controls onto a phone width. Prioritize map, playback/recording and SOS, then move secondary tools into a predictable menu/sheet.
- **Interaction fidelity:** preview opened/closed panels, click targets, cancel/confirm/error, navigation, focus return and scroll containment. Interactive mockups are **simulations**; do not falsely claim they perform GNSS, SOS, recording, ACK or saved evidence.
- **Independent self-critique before review:** run a brief adversarial pass across every affected surface: *What is redundant, confusing, clipped, illegible, displaced, unreachable, inconsistent, or misleading?* Correct issues without repeatedly recapturing unaffected screens. Inspect one representative rendered state per important layout/state change, plus focused interaction/overflow checks.

**Stop conditions:** if the proposal has known material defects, clearly label it **not ready** and do not seek approval. Provide the concrete defects and corrected exact-app proposal first. Approval must name the specific version, screen scope and design artifact; otherwise remain in design-only mode. No runtime UI implementation from a merely discussed or superseded proposal.
